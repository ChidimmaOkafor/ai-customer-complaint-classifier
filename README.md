# AI Customer Complaint Classifier

A small, end-to-end machine learning application that automatically classifies customer complaints into predefined categories, built as a SIWES (internship) final project. The system exposes a REST API that receives a complaint, predicts its category using a trained ML model, and persists both the complaint and the prediction to a database.

## Project Overview

Companies receive a high volume of customer complaints every day, covering a wide range of issues — failed payments, login problems, technical faults, and general enquiries. Manually reading and routing each complaint to the right team is slow and inconsistent.

This project builds a lightweight system that automatically reads an incoming complaint message and predicts which category it belongs to, using a machine learning model trained on a labeled dataset of past complaints. Every complaint and its prediction are saved to a database so they can be reviewed or retrieved later.

## Problem Statement

Support teams need a fast, consistent way to triage incoming complaints. Without automation, complaints are categorized manually, which is time-consuming and prone to human inconsistency, especially as volume grows. There was no existing lightweight tool for this internship's context that could take a raw complaint message and immediately return a predicted category with a confidence score.

## Project Objectives

- Build a small, working, understandable application rather than an over-engineered one.
- Demonstrate practical understanding of Python, machine learning, REST API design, and database integration.
- Train and compare at least two ML classification models and select the better-performing one.
- Expose the model through a FastAPI application with documented endpoints.
- Persist every complaint and its prediction to a database.
- Demonstrate correctness through basic automated tests.

## Key Features

- **Automatic complaint classification** into one of ~5 predefined categories.
- **Confidence score** returned alongside each prediction (the model's predicted probability for the chosen category).
- **Persistent storage** of every submitted complaint and its prediction in SQLite.
- **REST API** built with FastAPI, including interactive Swagger/OpenAPI documentation.
- **Complaint history retrieval** — list all complaints, optionally filtered by category, or fetch a single complaint by ID.
- **Health check endpoint** to verify the API, database connection, and model load status.
- **Input validation** with clear rejection of invalid requests (e.g. empty messages).
- **Basic automated test suite** using Pytest.

## System Architecture

The application follows the flow required by the project specification:

```
Customer Complaint (message)
        │
        ▼
   FastAPI endpoint (POST /complaints)
        │
        ▼
  TF-IDF Vectorizer (transforms text → numeric features)
        │
        ▼
   Trained ML Model (predicts category + confidence)
        │
        ▼
   SQLite Database (complaint, category, confidence, timestamp saved)
        │
        ▼
   JSON Response returned to client
```

Retrieval endpoints (`GET /complaints`, `GET /complaints/{id}`) read directly from the SQLite database via SQLAlchemy.

## Machine Learning Approach

The classifier is a traditional supervised text-classification pipeline (not a deep learning / transformer-based approach), chosen deliberately to match the scope of the project — small, explainable, and fast to train:

1. Raw complaint text is cleaned and normalized.
2. Text is converted into numeric features using **TF-IDF** (Term Frequency–Inverse Document Frequency).
3. A classification model is trained on the TF-IDF vectors to predict a category label.
4. At inference time, the same fitted TF-IDF vectorizer is used to transform new complaint text before it is passed to the model, ensuring training-time and inference-time features are consistent.

## Dataset and Preprocessing

- The dataset consists of customer complaint messages, each paired with a correct category label, in CSV format.
- **Categories (as specified in the project brief):**
  - Payment/Transaction
  - Account Access
  - Technical Issue
  - Customer Service
  - General Enquiry
  


**Preprocessing steps applied:**
- Rows with missing values in critical columns (`id`, `message`, `category`) were dropped.
- Complaint text was lowercased, and extra/irregular whitespace was collapsed and trimmed.
- Category labels were stripped of whitespace and normalized for consistency.
- The cleaned dataset was saved separately from the raw dataset so that training always runs against a consistent, cleaned CSV file.

## Model Training and Selection

Two classical ML models were trained and compared, as required by the project brief:

| Model | Library |
|---|---|
| Logistic Regression | `sklearn.linear_model.LogisticRegression` |
| Multinomial Naive Bayes | `sklearn.naive_bayes.MultinomialNB` |

**Training process:**
1. The cleaned dataset was split into training and test sets (80/20 split, fixed `random_state` for reproducibility).
2. `TfidfVectorizer` was fit on the training text and used to transform both the training and test sets.
3. Both models were trained on the TF-IDF-transformed training data.
4. Each model was evaluated on the held-out test set using accuracy and a full classification report (precision, recall, F1-score per category).

**Model comparison :**

| Model | Accuracy |
|---|---|
| Logistic Regression | 95%|
| Multinomial Naive Bayes | 90% |

## Classification Workflow

1. A client sends a complaint message to `POST /complaints`.
2. FastAPI validates the request body against the `ComplaintCreate` Pydantic schema.
3. The complaint text is transformed using the saved TF-IDF vectorizer.
4. The transformed vector is passed to the loaded classification model.
5. The model returns a predicted category and a confidence score (the maximum predicted class probability, from `predict_proba`).
6. The complaint, predicted category, confidence, and a server-generated timestamp are saved to the SQLite database.
7. The API responds with the complaint ID, category, and confidence score.

## Database Structure

A single `complaints` table, defined via SQLAlchemy ORM:

| Column | Type | Notes |
|---|---|---|
| `id` | Integer | Primary key, auto-incremented |
| `message` | String(600) | The complaint text, required |
| `category` | String(50) | Predicted category, required |
| `confidence` | Float | Model's confidence score for the prediction, required |
| `created_at` | DateTime | Defaults to UTC time at creation |

This satisfies the project requirement that each record contain, at minimum: an ID, the complaint message, the predicted category, and a creation date.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/complaints` | Submit a new complaint; returns the predicted category, confidence, and saved record ID. |
| `GET` | `/complaints` | Retrieve all saved complaints. Supports an optional `category` query parameter to filter results. |
| `GET` | `/complaints/{id}` | Retrieve a single complaint by its ID. Returns `404` if not found. |
| `GET` | `/health` | Returns API status, database connectivity, and whether the ML model is loaded. |

Interactive documentation is auto-generated by FastAPI and available at `/docs` (Swagger UI) and `/redoc`.

## Error Handling and Logging

- **Validation errors:** A custom exception handler catches `RequestValidationError` and returns a `422 Unprocessable Entity` response with details of what failed (e.g. an empty `message` field, which violates the `min_length=1` constraint on the schema).
- **Not found errors:** Requesting a complaint ID that doesn't exist returns a `404 Not Found` with a descriptive message.
- **Database errors:** Failures while saving a complaint are caught, the transaction is rolled back, the error is logged, and the exception is re-raised rather than silently swallowed.
- **Logging:** Python's built-in `logging` module is used to log validation failures and database errors for basic observability during development and demoing.

## Testing with Pytest

Basic tests were written using Pytest and FastAPI's `TestClient`, covering the scenarios required by the project brief:

- A valid complaint can be submitted and returns a prediction.
- Submitted complaints can be retrieved afterward.
- Invalid input (an empty `message`) is correctly rejected with a `422` status code.

Example test:

```python
def test_invalid_complaint():
    response = client.post(
        "/complaints",
        json={"message": ""}
    )
    assert response.status_code == 422
```

This is intentionally a small test suite — the goal specified by the project brief was to demonstrate understanding of testing fundamentals, not to build exhaustive test coverage.

## Limitations

- The model is trained on a relatively small, manually assembled dataset, so accuracy may drop on complaint phrasing not well represented in the training data.
- TF-IDF is a bag-of-words-style representation; it does not capture word order or deeper semantic meaning the way modern embedding-based approaches would.
- The confidence score is the model's raw predicted probability for the winning class — it reflects the model's internal certainty, not a guaranteed correctness rate.
- There is no authentication/authorization on the API; it is intended for demonstration purposes, not production deployment.
- No containerization (Docker) or dedicated performance/load testing was implemented as part of this iteration of the project.
- The application does not currently support editing or manually correcting a saved prediction after submission.

## Future Improvements

- Expand and diversify the training dataset to improve generalization.
- Experiment with additional models (e.g. Support Vector Machines, or embedding-based classifiers) beyond the two compared here.
- Add a lightweight human review/correction workflow so misclassified complaints can be relabeled and fed back into retraining.
- Add authentication for API access.
- Containerize the application with Docker/Docker Compose for easier deployment and environment consistency.
- Add performance/load testing to understand how the API behaves under concurrent requests.
- Add an analytics view (e.g. complaint volume by category over time).
- Move configuration (database URL, model paths) into environment variables for better deployment flexibility.
